# 个人亚马逊跟卖 + 采购自动化系统：需求分析与技术落地方案

> 分析对象：4 大模块（跟卖清洗、发货清洗通知、利润计算与商品库、1688 采购映射）
> 定位：个人单用户使用 · 数据源以 Excel/CSV 为主 · 通知推送到飞书
> 日期：2026-08-25

---

## 一、需求总览与总体评价

| 模块 | 功能 | 总体评价 |
|---|---|---|
| 1. 跟卖产品信息清洗与自动生成 | ASIN 信息清洗 → 按模板生成上架表格，自动填 SKU/库存/调价/采购上限 | 需求清晰，规则确定性高，**可行性高** |
| 2. 发货订单数据清洗与通知 | 清洗乱码 SKU、提取图片/跟踪号生成小图、飞书推送、当日利润初算 | 核心功能可行，**乱码 SKU 的历史映射是关键难点** |
| 3. 利润计算器与商品库管理 | 运费/偏远附加费计算、多批次重量、货代称重对比、商品库沉淀、利润报告 | 全部是表格运算类，**可行性最高** |
| 4. 1688 采购映射与采购单生成 | 商品库↔1688 链接映射、订单自动匹配采购信息、按模板生成采购表 | 核心映射可行，**"自动匹配"需设为人机协同** |

**总体结论：4 个模块均可落地，无技术上的"拦路虎"，主要风险集中在数据规则的一致性设计和 1688 数据获取方式的预期管理上。** 建议按"先跑通 1+2，再做 3，最后做 4"的路径分期实施。

## 二、功能矛盾点 / 冲突点分析（重点）

这里有 6 个问题值得在开发前理清，否则后期返工：

### 冲突 1：两套 SKU 体系无法直接关联（影响模块 2、3、4 全链路）
- 模块 1 生成**新规范 SKU**（4 位数字 + 颜色 + 尺码）
- 模块 2 的历史发货单上是**乱码旧 SKU**
- 模块 3 要求"跟卖数据与发货数据**统一去重**"

**矛盾**：新 SKU 与乱码旧 SKU 字符串对不上，商品库根本合并不起来，更谈不上 1688 匹配。
**解法**：必须建一张 **SKU 别名映射表**（旧乱码 SKU → 新 SKU → 产品唯一 ID）。首次上线时花 1-2 小时把你的历史 SKU 对照清单一次性导进去，日常增量维护。

### 冲突 2：重量口径不统一（模块 2 vs 模块 3 的利润结果会打架）
- 模块 2 初算利润用的是**发货单记录的重量**（渠道重量）
- 模块 3 的目标之一是**核查货代是否随意加重**

**矛盾**：如果货代的称重确实偏高（常见偏差 5%~20%），那模块 2 每天推给你的"利润初算"就是**虚高**的，两个模块会给出互相矛盾的数字，影响你调价的信心。
**解法**：定义**重量优先级**统一口径：`货代称重确认值 > 发货单记录重量 > SKU 历史批次均值`。初算先用发货单重量并**标注"未对账"**，货代清单回来后自动回填修正；同时做**差异告警**（货代称重 - 发货单重量超 ±X% 标红，X 可配置）。

### 冲突 3：利润报告依赖手填价格，数据质量取决于你的勤快程度
- 模块 1：价格、保低价「需要自己填写」
- 模块 3：利润分析报告「汇总真实成本」

**矛盾**：利润报告的口径如果包含售价/保低价，而这两个数是手填的，那么填得不准或不及时，报告就是错的。这不是功能冲突，而是**数据依赖的坑**。
**解法**：售价来源做成一个明确的三选一口径：① 手动录入目标售价（策略价）② 抓取当前 Listing 售价快照 ③ 两者取其一作为准账口径。建议用 ②（自动抓快照）为主、① 辅助，毕竟产品多的时候手填不现实。

### 冲突 4：4 位数字前缀的 SKU 容量与"颜色尺码字典"问题
- 4 位数字只有 **10000 个**前缀；SKU = 前缀 + 颜色 + 尺码，同前缀不同颜色尺码算不同 SKU
- 颜色尺码写法不统一会造成灾难：清洗时出现「Red / 红色 / 正红」会生成**两个 SKU**，商品库去重立刻失效（模块 3 整个逻辑崩掉）

**矛盾**：模块 1 的自由生成规则与模块 3 的严格去重天然冲突。
**解法**：
- 颜色、尺码**做成受控字典**（拼音 / 英文 / 中文做归一化映射），清洗时强制匹配字典，不在字典里的进"待确认"名单，而不是默默生成新值
- 前缀从「4 位数字」升级为「4 位数字分段或字母+数字」（如 `R1024`），避免像服帖「1-9999 用完」的问题；如果产品量小可维持 4 位纯数字，但要留好升级空间

### 冲突 5：跟卖自动调价的合规边界（模块 1 的"保低价"）
你的模块 1 说价格、保低价手填——这是**正确且安全**的做法，请坚持。补充一点：
- 建议**定时改价只做"生成改价清单 + 人工一键确认"**，不要做无人值守自动改价（亚马逊对跟卖频繁剧烈调价有风控，严重会警告/封号）
- 系统里把"手填价格"的流程定义清楚：清洗出表 → 你填价 → 表格状态从"待填价"→"已就绪"，确保没填价的产品不会被误上架

### 冲突 6：「自动识别亚马逊子 SKU 与 1688 匹配」的预期管理（模块 4）
1688 **对个人没有开放拿数据权限**，所以"自动匹配"不可能做到"从 1688 自动抓取全站商品"。
**现实解法**：映射关系 = **你粘贴 1688 链接 + 系统记住规格**（商品库录入时维护一次），之后订单来了系统按规格给出**候选匹配**，人工确认后自动带出 ID/链接/规格。即"半自动 + 人机协同"。这个预期必须先对齐，否则后期会觉得"不智能"。

## 三、优化建议（值得加进去的点）

1. **统一商品主数据（Product Master）**：一张核心表承载 `ASIN ↔ 新SKU ↔ 旧SKU ↔ 1688ID/链接 ↔ 采购价 ↔ 重量批次`，4 个模块全部引用它，而不是各自建库。这是整个系统最值得的一笔投资。
2. **默认值参数化**：库存 / 单次调整价 / 最大采购量做成配置项（不是写死在代码里），一次改全局生效。
3. **乱码清洗规则沉淀成字典**：你历史上遇到的乱码模式（如全角半角、错位替换）录成"清洗规则表"，处理过的自动积累，越用越准，不再每次手工看。
4. **利润分两层口径**：
   - **初算**（模块 2，订单级）：渠道重量 × 采购价，当天发货后 10 分钟看到数，标注"未对账"
   - **精算**（模块 3，商品级）：真实佣金 + 头程分摊 + 偏远附加费 + 采购实际成本
   - 报告里明确标注口径差异，避免自己看数字困惑
5. **偏远地区邮编表离线化**：建一张可导入导出的「邮编 → 附加费」表（按货代渠道分），平台支持你随时增删，不用每次调外部接口。
6. **关联键用产品 ID 而不是 SKU 字符串**：所有业务表用自增 `product_id` 关联，SKU 允许改名，否则改名会连锁反应。
7. **图片策略**：Excel 嵌入图片可直接提取（openpyxl）；外链图片下载后统一转 PNG 小图拼图（PIL），飞书一次发一张拼图而不是几十张单图。
8. **每日任务的幂等性**：同一天重复上传同一张发货表，#不重复推送不重复统计#，靠"日期 + 文件哈希"去重。

## 四、可行性评估

### 分模块评估

| 模块 | 可行性 | 关键依据与风险点 |
|---|---|---|
| 1. 跟卖清洗与生成 | **高** | pandas/openpyxl 处理表格是成熟方案；SKU 生成是纯规则计算。风险低 |
| 2. 发货清洗 + 飞书通知 + 利润初算 | **高** | Excel 解析可靠；嵌入图片提取 + PIL 拼图可行；飞书 API 发消息/图片成熟。风险点：**乱码 SKU 映射表首次要人工整理**（一次性投入） |
| 3. 利润计算器 + 商品库 + 称重对比 | **高** | 全部是表格运算：邮编匹配、两表 merge 算差异、多批次重量按字典存储。无外部依赖 |
| 4. 1688 映射 + 采购单生成 | **中~中高** | 映射关系靠人工粘贴链接维护（无 1688 API）；采购单按你的模板生成 Excel 可行。风险点：**"自动匹配"只能做到人机协同** |

### 技术风险清单（已按你确认的约束更新)

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| 个人微信无法自动化 | ✅ 已排除 | 你选了飞书，无此问题 |
| 1688 无开放 API | 中 | 用"粘贴链接 + 规格记忆 + 候选匹配"方案，不承诺全自动 |
| 发货单/货代单含 PDF | ✅ 已排除 | 你确认 Excel/CSV 为主；若未来出现 PDF 再加解析模块 |
| 乱码 SKU 历史数据 | 中 | 一次性映射表初始化 + 清洗规则字典持续积累 |
| 亚马逊数据源获取 | 低 | 你已有外部下载渠道（第三方工具导出），系统只做加工 |
| 飞书机器人配额 | 低 | 个人版足够每日消息/图片量；如需数据库可视化可升级用多维表格 |

## 五、技术落地方案

### 5.1 技术选型（以"个人单机 + 低运维"为原则)

| 层 | 选型 | 理由 |
|---|---|---|
| 形态 | 本地 Web 应用（浏览器上传/下载表格） | 你提到"上传到工作台"，Web 界面比命令行友好 |
| 后端 | Python + FastAPI | 生态里 pandas/openpyxl/PIL 都是事实标准，开发快 |
| 存储 | SQLite | 单用户零运维，文件即数据库，方便备份 |
| 飞书推送 | 飞书机器人（开放平台）+ 图片上传 API | 发消息 + 发拼图；插件环境已集成 Lark 能力可直接复用 |
| 定时 | APScheduler 或 cron | 每天固定点跑"发货清洗 + 推送" |
| 前端 | 简单 HTML + 上传控件（可不上框架） | 单用户，够用即可 |

### 5.2 核心数据模型（关键表)

```
product_master           商品主数据      product_id / asin / 名称 / 类目 / 采购价 / 采购链接 / 1688_id / 状态
sku_alias_map            SKU 映射        old_sku(乱码) / new_sku / product_id       ← 冲突1的解法
sku_defaults_config      跟卖默认值配置   inventory / adjust_price / max_purchase   ← 可改默认值
dict_color / dict_size   颜色尺码受控字典  标准值 / 别名列表                          ← 冲突4的解法
shipping_orders_clean    清洗后发货订单   日期 / new_sku / 跟踪号 / 渠道 / 重量 / 图片路径
weight_history           重量批次表      product_id / 日期 / 渠道 / 重量 / 来源(发货单|货代|手动)
courier_weight_check     称重对比结果    order_no / 发货单重量 / 货代重量 / 差异% / 是否告警
freight_template         运费模板       渠道 / 首重续重单价
postcode_surcharge       偏远邮编附加费  邮编段 / 渠道 / 附加费                            ← 离线化
price_history            售价/保低价历史  product_id / 日期 / 售价 / 保低价 / 来源         ← 冲突3的解法
purchase_orders_1688     1688 采购单     批次 / 1688链接 / 规格信息 / 数量 / 采购地址
```

### 5.3 模块落地方式

**模块 1（跟卖清洗+生成）**
- 上传跟卖数据表 → 按清洗规则（去重/归一/字典匹配）→ 按模板生成上架表
- SKU 由规则引擎生成：`前缀 + 颜色码 + 尺码`，颜色/尺码强制查字典
- 库存、单次调整价、最大采购量读取配置默认值；价格/保低价列留空标黄「待填价」
- 产出：上架 Excel + 「待填价」清单

**模块 2（发货清洗+通知）**
- 每天定时（或手动上传）→ 乱码 SKU 过映射表还原 → 提取图片/跟踪号/SKU → 生成当日拼图
- 拼图 + 当日汇总消息推送到飞书
- 利润初算：`渠道重量 × 采购成本`，标注"未对账"，渠道重量来源取发货单
- 产出：清洗后订单表 + 飞书拼图消息 + 初算结果

**模块 3（利润计算+商品库+对账）**
- 运费计算：运费模板 + 偏远邮编附加费匹配
- 重量：支持手填 / 自动取发货单 / 保持一 SKU 多批次历史（按 product_id 存列表）
- 称重对账：导入货代称重清单 → 与发货单/历史比对 → 差异超阈值自动标红告警
- 利润报告：**精算口径**（佣金+运费分摊+附加费+采购成本），按产品维度产出报告辅助调价
- 产出：对账报表 + 利润分析报告

**模块 4（1688 映射+采购单）**
- 商品库录入时粘贴 1688 链接并维护规格信息（一次性映射）
- 上传订单 → 系统按 SKU/规格给出候选匹配 → 人工确认 → 自动带出 1688 ID/链接/规格/数量
- 按你的采购模板生成 1688 采购订单 Excel（含采购地址）
- 产出：1688 采购订单表

## 六、分期实施路径（建议)

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| **阶段 1（MVP 闭环）** | 模块 1 清洗+SKU 生成 + 模块 2 发货清洗 + 飞书拼图通知 + 利润初算 | 用你的真实表格跑通"上传→清洗→飞书收到图"全流程 |
| **阶段 2** | 模块 3：运费/附加费计算 + 商品库沉淀 + 多批次重量 + 称重对比告警 | 能对账当月所有货代重量并出差异报告 |
| **阶段 3** | 模块 4：1688 映射 + 采购单生成 | 一键生成 1688 采购订单表 |
| **阶段 4** | 利润精算报告 + 历史数据回流（把之前的数据灌进商品库） | 报告辅助你完成一轮调价决策 |

## 七、验证方式

1. **真实样例回测**：用你最近 1-2 周的跟卖表 + 发货表跑一遍清洗，与手工处理结果逐条对比，验证准确率（目标 100% 可识别、0 串行）
2. **乱码覆盖清单自行核对**：历史乱码 SKU 全部过映射表后，无遗漏
3. **飞书推送联调**：拼图消息实际收到、图片清晰可扫码/看单
4. **利润交叉验证**：随机抽 5 个订单，系统初算 vs 人工计算一致
5. **称重对比抽查**：货代清单差异超阈值的产品能正确标红
6. **采购单比对**：生成的 1688 采购单与你手做的对照一致（ID、规格、数量、地址）

## 八、给用户的 3 条核心建议（摘要）

1. **先建商品主数据 + SKU 映射表**，这是 4 个模块能否打通的总开关，值得最先投入
2. **接受"人机协同"**：价格手填、1688 匹配人工确认、改价人工确认——这些不是系统做不了，而是**安全和现实（1688 无 API）的正确做法**
3. **按阶段 1 → 4 分期做**，先跑通"上传→清洗→飞书看图"再扩展，避免一次性做完 4 个模块发现数据口径对不上
