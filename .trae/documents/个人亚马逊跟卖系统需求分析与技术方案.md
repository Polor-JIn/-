# 个人亚马逊跟卖 + 采购自动化系统：需求分析与技术落地方案

> 分析对象：4 大模块（跟卖清洗、发货清洗通知、利润计算与商品库、1688 采购映射）
> 定位：个人单用户使用 · 数据源以 Excel/CSV 为主 · 通知推送到飞书
> 日期：2026-08-25

---

## 一、需求总览与总体评价

| 模块 | 功能 | 总体评价 |
|---|---|---|
| 1. 跟卖产品信息清洗与自动生成 | ASIN 信息清洗 → 按模板生成上架表格，自动填 SKU/库存/调价/采购上限 | 需求清晰，规则确定性高，**可行性高** |
| 2. 发货订单数据清洗与通知 | 清洗乱码 SKU、提取图片/跟踪号生成小图、飞书推送、当日利润初算 | 核心功能可行，**乱码 SKU 的历史映射是关键难点** |
| 3. 利润计算器与商品库管理 | 运费/偏远附加费计算、多批次重量、货代称重对比、商品库沉淀、利润报告 | 全部是表格运算类，**可行性最高** |
| 4. 1688 采购映射与采购单生成 | 商品库↔1688 链接映射、订单自动匹配采购信息、按模板生成采购表 | 核心映射可行，**"自动匹配"需设为人机协同** |

**总体结论：4 个模块均可落地，无技术上的"拦路虎"，主要风险集中在数据规则的一致性设计和 1688 数据获取方式的预期管理上。** 建议按"先跑通 1+2，再做 3，最后做 4"的路径分期实施。

## 二、核心机制设计（按最新澄清定稿）

### 2.1 SKU 体系：新品规范 SKU + 老品乱码 SKU 并存（不再是冲突，而是统一模型）
- **新品**（模块 1）：从未上架 → 生成新规范 SKU `4 位数字前缀 + 颜色 + 尺码`
- **老品**（模块 2）：亚马逊后台已有、SKU 为乱码 → **字符串不可改，原样保留**
- 商品库内部统一用自增 `product_id` 关联；一个产品可挂多个 SKU 别名（新规范 SKU / 历史乱码 SKU），各自独立、互不冲突
- **4 位前缀 = 产品号**：同一款不同颜色/尺码共用同一前缀，`前缀+颜色+尺码` 联合唯一。1 万个前缀对应 1 万个产品，个人使用足够

### 2.2 去重机制：系统自动过滤 + 冲突转人工（不是按钮，是入库过滤）
- 去重是**系统自动行为**，核心规则（入库时自动执行，无需手动按键）：
  - 录入/导入时按**去重键**自动比对商品库
  - **完全一致** → 自动跳过，不重复录入（顺带合并/累计该 SKU 的历史批次重量）
  - **关键字段不一致**（如售价、成本、采购价等单值属性）→ 自动转**人工审核队列**，不静默覆盖；注：重量是批次变量，永远累积不判重
- 去重键（匹配维度）：**SKU**（新规范 SKU = `前缀+颜色+尺码` 天然唯一；老品乱码 SKU 用其字符串本身，同样唯一）

### 2.3 重量：两种用途互不干扰 + 明确优先级
- **模块 2 利润初算** = 当日发货日账（用发货单当日重量），口径明确、只反映当天
- **模块 3 称重对账** = 长期重量校准，确认后的重量回填商品库，供后续精算；不影响当日日账
- **重量优先级（可信度从高到低）**：
  `货代确认重量 / 自己实测重量 > 发货单当日重量 > SKU 历史批次均值 > 参考重量(预估兜底)`
- **缺重量 → 预估兜底**：无重量信息时用「历史批次均值 + 商品库手填参考重量（1+2 结合）」给**参考重量**，算出预估售价/保底价并明确标注"预估"，重量确认后一键重算
- 对账差异超过阈值（±3%~5%，可配置）→ 自动标红告警

### 2.4 售价与保底价（解决"缺重量时价格怎么定"的待决问题）
| 字段 | 来源 | 缺重量时的表现 |
|---|---|---|
| **售价** | 抓取当前/历史零售价快照作参考 | 快照不依赖重量，照常给出 |
| **保底价** | **成本公式反推计算**（采购成本 + 头程均摊 + 平台佣金 + 配送费 + 预估运费(含偏远附加费) + 目标毛利），不靠抓价 | 用参考重量算出**预估保底价**，标"预估"，确认重量后自动重算 |

### 2.5 颜色尺码字典（不影响匹配，反而是匹配前提）
- 字典 = 「别名 → 标准值」表（`Red / 正红 / 红色 → 红色`），跟卖数据可能是英文、发货单是中文，**靠字典归一化后两边才能匹配同一款**
- 新值出现 → 进"待确认"队列，确认一次自动进字典，收敛写法而非丢数据
- 没有字典时 `Red` 和 `红色` 会被当成两款 → 去重失败；有字典则正确合并

### 2.6 模块 1 交付形态（按你的要求，不自动上架）
- 系统只**生成 Excel 表格**（含自动填好的 SKU/库存/调价/采购上限 + 留空高亮的"待填价"列）
- 你后续把表上传到其他 ERP 系统上架；系统不做任何自动上架/改价

### 2.7 1688 自动匹配的预期管理（模块 4）
- 1688 对个人无开放数据 API → "自动匹配" = **粘贴 1688 链接 + 系统记忆规格 + 候选匹配 + 人工确认**（半自动 + 人机协同）

## 三、优化建议（值得加进去的点）

1. **统一商品主数据（Product Master）**：一张核心表承载 `product_id ↔ 新SKU ↔ 历史乱码SKU ↔ ASIN ↔ 1688ID/链接 ↔ 采购价 ↔ 重量批次`，4 个模块全部引用它，而不是各自建库。这是整个系统最值得的一笔投资。
2. **默认值参数化**：库存 / 单次调整价 / 最大采购量做成配置项（不是写死在代码里），一次改全局生效。
3. **乱码清洗规则沉淀成字典**：你历史上遇到的乱码模式（如全角半角、错位替换）录成"清洗规则表"，处理过的自动积累，越用越准，不再每次手工看。（注意：罗马衬衣的乱码是随机无规律的，只能人工对照，走映射表方式）
4. **利润分两层口径**：
   - **初算**（模块 2，订单级日账）：发货单当日重量 × 采购价，当天发货后即可看到
   - **精算**（模块 3，商品级）：确认重量 + 真实佣金 + 头程分摊 + 偏远附加费 + 采购实际成本
   - 报告里明确标注口径差异，避免自己看数字困惑
5. **偏远地区邮编表离线化**：建一张可导入导出的「邮编 → 附加费」表（按货代渠道分），平台支持你随时增删，不用每次调外部接口。
6. **关联键用产品 ID 而不是 SKU 字符串**：所有业务表用自增 `product_id` 关联，SKU 允许改名，否则改名会连锁反应。
7. **图片策略**：Excel 嵌入图片可直接提取（openpyxl）；外链图片下载后统一转 PNG 小图拼图（PIL），飞书一次发一张拼图而不是几十张单图。**发货通知用发货单嵌入图，多单拼一张大图**。
8. **每日任务的幂等性**：同一天重复上传同一张发货表，不重复推送不重复统计，靠"日期 + 文件哈希"去重。
9. **冲突清单**：去重时若匹配到但关键字段不一致，单独列出"待人工审核"清单，不静默覆盖。

## 四、可行性评估

### 分模块评估

| 模块 | 可行性 | 关键依据与风险点 |
|---|---|---|
| 1. 跟卖清洗与生成 | **高** | pandas/openpyxl 处理表格是成熟方案；SKU 生成是纯规则计算。风险低 |
| 2. 发货清洗 + 飞书通知 + 利润初算 | **高** | Excel 解析可靠；嵌入图片提取 + PIL 拼图可行；飞书 API 发消息/图片成熟。风险点：**乱码 SKU 映射表首次要人工整理**（一次性投入） |
| 3. 利润计算器 + 商品库 + 称重对比 | **高** | 全部是表格运算：邮编匹配、两表 merge 算差异、多批次重量按字典存储。无外部依赖 |
| 4. 1688 映射 + 采购单生成 | **中~中高** | 映射关系靠人工粘贴链接维护（无 1688 API）；采购单按你的模板生成 Excel 可行。风险点：**"自动匹配"只能做到人机协同** |

### 技术风险清单（已按你确认的约束更新)

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| 个人微信无法自动化 | ✅ 已排除 | 你选了飞书，无此问题 |
| 1688 无开放 API | 中 | 用"粘贴链接 + 规格记忆 + 候选匹配"方案，不承诺全自动 |
| 发货单/货代单含 PDF | ✅ 已排除 | 你确认 Excel/CSV 为主；若未来出现 PDF 再加解析模块 |
| 乱码 SKU 历史数据 | 中 | 一次性映射表初始化 + 清洗规则字典持续积累 |
| 亚马逊数据源获取 | 低 | 你已有外部下载渠道（第三方工具导出），系统只做加工 |
| 飞书机器人配额 | 低 | 个人版足够每日消息/图片量；如需数据库可视化可升级用多维表格 |

## 五、技术落地方案

### 5.1 技术选型（以"个人单机 + 低运维"为原则)

| 层 | 选型 | 理由 |
|---|---|---|
| 形态 | 本地 Web 应用（浏览器上传/下载表格） | 你提到"上传到工作台"，Web 界面比命令行友好 |
| 后端 | Python + FastAPI | 生态里 pandas/openpyxl/PIL 都是事实标准，开发快 |
| 存储 | SQLite | 单用户零运维，文件即数据库，方便备份 |
| 飞书推送 | 飞书机器人（开放平台）+ 图片上传 API | 发消息 + 发拼图；插件环境已集成 Lark 能力可直接复用 |
| 定时 | APScheduler 或 cron | 每天固定点跑"发货清洗 + 推送" |
| 前端 | 简单 HTML + 上传控件（可不上框架） | 单用户，够用即可 |

### 5.2 核心数据模型（关键表)

```

sku_alias_map            SKU 映射        old_sku(乱码) / new_sku / product_id         ← 罗马衬衣乱码走人工对照映射
sku_prefix_counter       前缀分配         product_id / prefix(4位) / 已用颜色尺码组合   ← 同一款共用同一前缀
sku_defaults_config      跟卖默认值配置   inventory / adjust_price / max_purchase     ← 可改默认值
dict_color / dict_size   颜色尺码受控字典  标准值 / 别名列表                            ← 归一化匹配前提
dedup_review_queue       去重人工审核      match_key / 冲突字段 / 旧值 / 新值 / 状态     ← 不一致转人工
shipping_orders_clean    清洗后发货订单   日期 / sku / 跟踪号 / 渠道 / 重量 / 图片路径   ← sku 可为乱码或新规范

courier_weight_check     称重对比结果    order_no / 发货单重量 / 货代重量 / 差异% / 是否告警
freight_template         运费模板       渠道 / 首重续重单价

price_history            售价/保底价历史  product_id / 日期 / 售价 / 保底价 / 来源(快照|公式|手动)
```

### 5.3 模块落地方式

**模块 1（跟卖清洗+生成）**
- 上传跟卖数据表 → 按清洗规则（去重/归一/字典匹配）→ 按模板生成上架表
- SKU 由规则引擎生成：`前缀 + 颜色码 + 尺码`，颜色/尺码强制查字典
- 库存、单次调整价、最大采购量读取配置默认值；价格/保低价列留空标黄「待填价」
- 产出：上架 Excel + 「待填价」清单

**模块 2（发货清洗+通知，当日日账）**
- 每天定时（或手动上传）→ 乱码 SKU 过映射表还原 → 提取发货单嵌入图片/跟踪号/SKU → 生成当日**多单拼一张大图**
- 拼图 + 当日汇总消息推送到飞书
- 利润初算：`发货单当日重量 × 采购成本`，口径明确只反映当天（不参与长期校准）
- 产出：清洗后订单表 + 飞书拼图消息 + 当日利润初算

**模块 3（利润计算+商品库+对账）**
- 运费计算：运费模板 + 偏远邮编附加费匹配
- 重量：支持手填(参考重量) / 自动取发货单 / 货代确认 / 保持一 SKU 多批次历史（按 product_id 存列表）；缺重量时用「历史均值 + 手填参考重量」兜底出预估值
- 称重对账：导入货代称重清单 → 与自己的称重比对 → 差异超阈值(±3%~5%可配置)自动标红告警
- 保底价由成本公式计算（采购+头程+佣金+配送+运费+毛利），售价取零售价快照；重量变动后支持一键重算
- 利润报告：**精算口径**（确认重量+佣金+运费分摊+附加费+采购实际成本），按产品维度产出报告辅助调价
- 产出：对账报表 + 利润分析报告 + 待审核冲突清单

**模块 4（1688 映射+采购单）**
- 商品库录入时粘贴 1688 链接并维护规格信息（一次性映射）
- 上传订单 → 系统按 SKU/规格给出候选匹配 → 人工确认 → 自动带出 1688 ID/链接/规格/数量
- 按你的采购模板生成 1688 采购订单 Excel（含采购地址）
- 产出：1688 采购订单表

## 六、分期实施路径（建议)

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| **阶段 1（MVP 闭环）** | 模块 1 清洗+SKU 生成 + 模块 2 发货清洗 + 飞书拼图通知 + 利润初算 | 用你的真实表格跑通"上传→清洗→飞书收到图"全流程 |
| **阶段 2** | 模块 3：运费/附加费计算 + 商品库沉淀 + 多批次重量 + 称重对比告警 | 能对账当月所有货代重量并出差异报告 |
| **阶段 3** | 模块 4：1688 映射 + 采购单生成 | 一键生成 1688 采购订单表 |
| **阶段 4** | 利润精算报告 + 历史数据回流（把之前的数据灌进商品库） | 报告辅助你完成一轮调价决策 |

## 七、验证方式

1. **真实样例回测**：用你最近 1-2 周的跟卖表 + 发货表跑一遍清洗，与手工处理结果逐条对比，验证准确率（目标 100% 可识别、0 串行）
2. **乱码覆盖清单自行核对**：历史乱码 SKU 全部过映射表后，无遗漏
3. **飞书推送联调**：拼图消息实际收到、图片清晰可扫码/看单
4. **利润交叉验证**：随机抽 5 个订单，系统初算 vs 人工计算一致
5. **称重对比抽查**：货代清单差异超阈值的产品能正确标红
6. **采购单比对**：生成的 1688 采购单与你手做的对照一致（ID、规格、数量、地址）

## 八、给用户的 3 条核心建议（摘要）

1. **先建商品主数据 + SKU 映射表**，这是 4 个模块能否打通的总开关，值得最先投入
2. **接受"人机协同"**：价格手填、1688 匹配人工确认、改价人工确认——这些不是系统做不了，而是**安全和现实（1688 无 API）的正确做法**
3. **按阶段 1 → 4 分期做**，先跑通"上传→清洗→飞书看图"再扩展，避免一次性做完 4 个模块发现数据口径对不上
